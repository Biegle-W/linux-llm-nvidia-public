# Engine update runbook (hands-on)

Since 2026-11-09 engine updates are installed by hand by the maintaining agent, not by the nightly script. The timer `nvidia-daily-engine-update.timer` stays **disabled**. `scripts/daily_engine_update.py` is kept as a toolbox: its read-only discovery and its single-profile short DSH check are still the right tools, but it no longer builds, promotes or pushes on a schedule.

Why: the unattended updater rejected good upstream releases over its own harness bugs and then stopped retrying them (HyperQwen bin/ relocation, Maya test environment and timeouts, a Strata hotfix control package). Watching each step is faster than hardening the script for every upstream change.

Promotion policy is unchanged: promote unless it really breaks ([policy](DAILY-ENGINE-UPDATE-POLICY.md)). A real break is a failed load, DSH, tool call or unload, invalid output, under half the decode/prefill speed, or over 3x TTFT. Smaller slowdowns are warnings. Re-run once before rolling back on speed alone; a new engine's first load can pay a one-time cost (Strata 0.2.13 DeepSeek: 66 s first TTFT, 6.1 s on the repeat).

## Daily check

```bash
cd ~/Desktop/linux-llm-nvidia
gpu-unlock-health status --brief            # must say VERIFIED; never create data/GPU-LOCK by hand
systemctl --user is-enabled nvidia-daily-engine-update.timer   # expect: disabled
python3 $PWD/scripts/daily_engine_update.py --check-only        # read-only discovery, no GPU
```

`--check-only` may report `rejected-revision-not-retried`; that list in `data/daily-update/state.json` belongs to the retired script and does not block a hands-on install.

## Install steps (every engine)

0. **Research first** (owner's rule since 2026-11-15). Before anything is installed, read what the new version changes: release notes, changelog, the diff against the installed commit and recent issues. Write down the bug fixes and speed changes that apply to this hardware, changed defaults or settings, and open regressions, and use that list to choose what to look at in the checks. Staging in isolation may run meanwhile. The summary goes into the evidence file and the report to the owner.
1. **Idle.** Router idle and unloaded, both GPUs at ~1 MiB, unlock VERIFIED.
2. **Stage in isolation** under `runtimes/<engine>-manual/<rev>-<date>/` (or reuse a complete staging dir and its `build-receipt.json`). Nothing in production changes.
3. **Baseline production** with the short DSH check, one profile at a time, calling the script by **absolute path** (its reservation owner check matches its own command line):
   `python3 $PWD/scripts/daily_engine_update.py --smoke-current PROFILE`
   then the gBench chat-template check (warms the model, six cases within 120 s, unloads):
   `python3 scripts/gbench_template_check.py --model PROFILE`
4. **Swap with pre-images** into `data/<engine>-update-<date>/preimages/` and write a `rollback.sh` beside them before anything is replaced.
5. **Check the new version** with the same two commands; compare with the baseline. A structured chat-template case that fails while its twin passes is a real break (template or serialization); see [GBENCH-TEMPLATE-CHECK-20261123.md](evidence/GBENCH-TEMPLATE-CHECK-20261123.md).
6. **Keep or roll back.** Roll back only on a real break (`rollback.sh`). Leave serving idle and unloaded.
7. **Record:** pin in `config/daily-update-versions.json`, a dated entry at the top of `docs/DAILY-ENGINE-UPDATES.md`, `docs/CURRENT-STATE.md` if a version changed. Commit, export to the public checkout (`python3 scripts/sync_public.py ../linux-llm-nvidia-public`, check the diff for secrets and home paths), commit there, and push both. Hold the push and ask the owner only if something big changed (a rollback or real break, a profile added/retired, deletions, serving or guard changes, anything about keys, privacy or the public export list).

## Working over SSH

- `scripts/visible_terminal.py` cannot open a terminal from an SSH session when no desktop session is reachable (`Visible harness terminal did not start`). Run the short checks headless in that case; nothing has started when that error appears.
- The Tailscale link can drop for a minute at a time. Start the build and each check detached on the server (`setsid nohup ... &`), write a `.done` file at the end, guard against a double start with a `.started` file, and poll with short SSH calls. Do not hold one SSH session open for the whole step.
- Take every baseline first, then build and download, then swap one engine at a time: a download or a build next to a check also lands in the numbers. One detached script per step with the idle gate inside it (unlock VERIFIED, router idle, GPUs empty) keeps the swap and its checks together when the link drops.
- While a check is running, do not start a build or a search over the whole checkout (`grep -r` from the repo root walks `models/` and `runtimes/`): the disk load lands in the SSD-streaming numbers. Search `docs/`, `scripts/`, `config/` and `tests/` by name.

## Engine notes

**HyperQwen** (`qwen27b-hyperqwen`). Production is the environment `runtimes/env-hyperqwen`. Build a copy: copy the env, `pip install --upgrade -r docker/requirements.txt`, delete and force-reinstall the same `vllm` wheel, `patches/apply.sh` then `apply.sh --kvarn`, `compileall`. Then rewrite **every** staging-path reference in `bin/` to the production path. pip writes both `#!<env>/bin/python` shebangs and `#!/bin/sh` + `'''exec' <env>/bin/python` trampolines; the old script only fixed the first kind. Then swap the env folder. Always delete the `vllm` package folder before the reinstall: `apply.sh` refuses to run over a copied tree whose `.hyperqwen-patches` stamp still matches an older series. Check the build log for one `== ` line per patch in `patches/series` plus the 4 KVarN patches and no `FAILED`. Production runs `bin/vllm` directly from `config/maintained-profiles.json` and uses none of the upstream launchers, so launcher and Docker changes upstream do not apply here. New `VLLM_*` variables change the compile-cache key, so the first load after an update may recompile once; judge speed on the repeat run. For a second update on the same day, suffix the folder (`data/hyperqwen-update-20261109b`).

**Strata** (`flash-next-strata`, `inkling-strata`, `hy4-flash-strata`; `deepseek-unsloth-strata` is frozen at 0.2.13). Strata 0.2.14 dropped DeepSeek: its `serve/server.py` refuses a DeepSeek config and the feed only carries the old 0.1.59 DSV4.1 package. Update control and the Qwen and Hy4 engines, and leave `runtimes/strata-unsloth-029`, `config/deepseek-unsloth-runtime.json` and `ENGINE_VERSION` alone; the DeepSeek steps below are kept for reference. The release tag and the hotfix tag differ (v0.2.14 against v0.2.14.1 for control 0.1.60.1): the pin is the release tag the checker reports. Use the release's signed `strata-feed.json`: it names the control package and the cuda13 `engine` and `dsv41` packages, so pick by feed entry, not by asset-name regex (hotfix releases carry extra control assets). Verify the feed signature and every package with upstream `strata_control` signing. The control version (e.g. 0.1.59.1) may differ from the engine version (0.1.59):
On an engine change move the Flash-Next preset (`qwen-flash-next.json`) to the new `exe`, `lib_dirs` and `cwd` and save it as a pre-image. The feed's `engine` and `dsv41` sections have no top-level `version`, and the DSV4.1 URL points at the 0.2.13 release, so read versions from the package file names. Read the release notes for changed defaults: the server sets engine variables for every start unless the preset's `env` names them (0.2.17 turned `STRATA_ROUTE_TAIL_SKIP` off this way, about 20% lower generation on `flash-next-strata`). Compare the preset file hashes before and after the first starts of a new control version, since upstream migrates its own configs on update.
- control → `runtimes/strata-terminal/terminal/<control>` with `serve/server.py` passed through `native_idle_policy.transform(..,'strata')`, then repoint `current`;
- Since 0.2.20 the Flash-Next presets may run an older Qwen engine than control (0.1.65 under control 0.1.66, from `runtimes/strata-manual/0.2.19-20261122/packages/qwen`): Qwen engine 0.1.66 slowed `flash-next-strata` 12-14% (and failed the since-retired UD-IQ4_XS entry), and 0.1.67 (0.2.21) slowed it 11-12% again, and 0.1.69 (0.2.22) 13-17%, so control 0.1.69 still runs engine 0.1.65. Try each new Qwen engine on `flash-next-strata` before moving its preset. Start `scripts/daily_engine_update.py --smoke-current` by its absolute path: the updater checks its own command line for that path and otherwise refuses with "Missing exact updater reservation".
- For Hy4, read the signed feed first: a release does not always carry a new CUDA 13 `strata-hy4` package (0.2.19 shipped 0.1.65 for Intel SYCL only and its feed still named the 0.1.64 package from v0.2.18). When the feed entry's `manifest_sha256` equals the installed `engine-component.json` hash in `config/hy4-flash-strata-runtime.json`, there is nothing to install: leave the Hy4 preset and that config alone and only run the Hy4 short check, since Hy4 is served through the new control. Otherwise fetch and verify the CUDA 13 `strata-hy4` package the feed names. Install it under `runtimes/strata-hy4/` with control, update the engine directory, build and hashes in `config/hy4-flash-strata-runtime.json`, and point the private Hy4 preset’s `exe` and `lib_dirs` there. Run the paired short check and owned unload for Hy4 as well as Flash-Next.
- Flash-Next launch cfg `~/.local/state/strata/launch/qwen-flash-next.json`: `exe`, `lib_dirs` → the qwen package, `cwd` → the new control folder (the file holds keys: never print it);
- DeepSeek: swap `runtimes/strata-unsloth-029/engine` (dsv41 package) and `source` (tag checkout, transformed `serve/server.py`), regenerate `config/deepseek-unsloth-runtime.json` hashes, and set `engine_version` and `ENGINE_VERSION` in `scripts/strata_unsloth_runtime.py` to the **engine** version.

**Maya** (`glm-maya`, `deepseek-maya`, `hy4-flash-maya`). Native build with the repo patches (see `scripts/update_native_builders.py`; names in `MAYA_CACHE_PATCH` and `MAYA_QUALIFICATION_PATCH`). The patches are applied with no fuzz, so an upstream edit next to a patched line stops the build: regenerate the patch from the patched tree under a new version suffix, point the two names at it and add it to `scripts/sync_public.py`; keep the old files for `update_reviewed.py`. Its upstream test suite needs `STRATA_PYTHON` (project-maya venv), `STRATA_GGUF_PY` (`build/_deps/strata_llamacpp-src/gguf-py`) and `STRATA_GLMD_FIXTURES` (a run-local folder), and per-test timeouts well above 120 s. `*_sm70` tests target Volta and do not apply to sm_86. Kernel-tolerance failures are warnings; the DSH check decides. Install the GLM and DeepSeek pins and swap `runtimes/project-maya`. For Hy4, verify CUDA 13 linkage with `ldd` and copy `build/maya-hy4` from the same build as the installed `serve/server.py` to its own versioned directory. Update the source commit, binary path and hash in `config/maya-hy4-runtime.json` and the private config’s `exe` together. Run the paired short check and owned unload for all three entries. The grouped automatic builder defers this install to the operator. Since 1.1.59 the engine reads its settings as `MAYA_X`; an older `STRATA_X` is copied to `MAYA_X` at start only when `MAYA_X` is not set, so set the `MAYA_` name in launch settings and never both. The CMake build options keep their `STRATA_` names. A patch that applies with line offsets only is fine as it is (1.1.67 took both 1.1.65 patches unchanged); refresh one only when a hunk is rejected. Since 1.1.75 the CMake options are `MAYA_*` too; `cmake/maya_old_names.cmake` still maps the builder's `-DSTRATA_X` options to `MAYA_X`, but patch hunks must use the new names (`maya-qualification-v1178.patch`). The builder replaces `maya-hy4` in place at the path in `config/maya-hy4-runtime.json` (still `runtimes/maya-hy4-v1174/`). Since 1.1.78 `hy4-flash-maya` measures a prompt route for 5-7 minutes before its first answer on every start until the timing settles (`runtimes/project-maya/data/hy4-prompt-route.txt`); a stop during that measurement can outlast the 20 s wrapper wait and fail the owned unload. Judge Hy4 on a re-run, and do not send a stop in its first minutes.

**sglang** follows the same pattern with `scripts/update_builders.py` / `update_native_builders.py` as the reference for build flags and pinned manifests. **llama.cpp** (`kolibri-llamacpp`) runs a build of the unmerged pull request ggml-org/llama.cpp#32891 at head `5f4d2228`, pinned in `pinned_profiles` of `config/daily-update.json` so no updater touches it. When the pull request merges or its head changes: build the new revision into its own folder under `runtimes/llamacpp-manual/` with `-DGGML_CUDA=ON -DCMAKE_CUDA_ARCHITECTURES=86` and gcc-13, run `test-backend-ops -o ROUND_NVFP4`, `-o LIGHTNING_INDEXER` and `-o FLASH_ATTN_EXT` on both cards, then update the binary path and the nine hashes in `config/kolibri-llamacpp-runtime.json` and the folder in `scripts/kolibri_llamacpp_runtime.py` together, and run the short check, gBench and owned unload. **ComfyUI, Raylight, Mesh, GGUF** are pinned and monitor-only; install one only when the owner asks.

**ComfyUI** (image and video entries). Review the upstream diff against `scripts/comfy_nodes`, `scripts/comfy_video_nodes` and the patched Raylight and mesh nodes first. Switch `runtimes/ComfyUI` and then `runtimes/ComfyUI-video` in place with `git checkout --detach <commit>`; do not move the folders (the video tree borrows the image tree's git objects). `runtimes/ComfyUI` is a partial clone: fetch from a full local clone with `git fetch --no-filter --refetch <clone> <commit>`. Install only the pins that changed in `requirements.txt` with `~/.local/bin/uv pip install --python runtimes/<env>/bin/python ...` in both `env-comfy` and `env-comfy-video` (dry-run first; PyTorch must not move, and never use `-r requirements.txt -U`). Regenerate both lock files with `uv pip freeze` and move the commit in `config/comfy-runtime.json` and `config/comfy-video-trial.json` and the release in `config/daily-update.json` in the same step, or the worker refuses to start. Check with `scripts/comfy_run.py` under a pty (`script -qefc`), before and after: both image models at 1024, both `--video-entry` models, and the Wan `prepare` and `raylight` stages. The script takes and releases its own GPU reservation.
