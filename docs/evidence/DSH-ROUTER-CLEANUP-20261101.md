# DSH router entries and harness compatibility — November 1, 2026

All nine maintained models are grouped under **NVIDIA Server Router** in the live web client and saved web/headless profiles. The existing internal provider ID, `nvidia-strata`, is retained for compatibility with web conversations. Engine-specific provider routes are merged, old selections are migrated, unrelated routes remain intact, and HyperQwen has one search-enabled picker entry. Engine labels in model names distinguish variants of the same model.

Every maintained entry explicitly declares its selected context, a 4,096-token output cap and the qualified non-thinking mode. Previously several live entries omitted the output cap and could inherit the harness's 32,768-token fallback, leaving insufficient room for system/tool instructions and user input on smaller contexts.

The HyperQwen search alias previously required the Responses API while DSH used Chat Completions. Registration-only checks did not expose this mismatch. The router now supports Chat Completions search: it obtains bounded web context and grounds the normal chat request while preserving function tools, history and streaming. Existing Responses search behavior remains supported. Search failure is explicit; it does not silently substitute an ungrounded answer.

The idle router was reloaded with the backend and DSH service invocations preserved. All 350 CPU regressions passed, including streaming Chat search with function tools. Two focused provider-migration checks passed after preserving the live provider ID. Actual short DSH checks and their scope are recorded in [the result summary](validation-results/20261101-dsh-router-cleanup.json).

Default validation is now a short actual harness tool call and completed result, followed by owned unload. Use `python3 scripts/smoke_dsh_tools.py --model super-vllm` from an appropriate visible terminal. The utility creates a tiny private fixture, stops extra answer generation after the completed tool result, and unloads only while ownership is unchanged. It does not run full-context retrieval, generation stress, repeated reload or a timed idle soak. Those require an explicit request.

## Desktop VRAM budget

The desktop now occupies part of the RTX 3080's VRAM. The old dense-engine startup check required 9,728 MiB free on that card, so it rejected the actual harness before inference. Lowering the KV cache alone exposed a second issue: the main model loaded, but the optional MTP draft failed during weight repacking.

HyperQwen now uses GPU-resident weights without the optional MTP draft, a 256 MiB KV cache per rank and a calculated 20,480-token context. This reduces KV allocation by 448 MiB per rank from the former 704 MiB setting. The conservative calculation uses the previous 704 MiB / 56,320-token ratio; the loader reported 24,094 KV tokens (1.18 times the selected context). Startup requires 9,728/8,960 MiB free on the 3080 Ti/3080. The independent 512 MiB runtime GPU reserve, host-memory, temperature, swap and telemetry guards remain enforced. Desktop applications are preserved, and CPU weight offload remains disabled.

The real DSH search alias, using a concise public topic query, returned a NASA source URL and the requested explanation, then unloaded. This checks the actual Chat Completions search path at short input length. Output was capped at 512 tokens; DSH reported max-tokens and a nonzero exit, but the observed explanation and source URL satisfy this bounded transport check. The answer was not independently fact-checked or validated for completeness. Actual harness inspection found that DSH appends a runtime snapshot with the user role. Search now ignores that known metadata message and skips background session-title generation. Regression cases cover both; genuine search failures remain explicit. Previous 56K retrieval and MTP speed results describe their dated configuration; they are not measurements of the new desktop-fit settings. No new full-context or speed test was run.
